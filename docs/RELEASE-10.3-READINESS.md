## Public operation and security

Independent public GETs at **23:14 UTC** against [giftportals.vercel.app](https://giftportals.vercel.app) returned:

| Endpoint | Observed result |
| --- | --- |
| `instant-cloud?action=status` | HTTP 200; creation available, both providers enabled, safety available, signed-direct upload and ten public examples. |
| `giftportals?action=status` | HTTP 200; legacy account API configured=false, generation/demo/signup disabled. |
| `giftportals?action=world` | HTTP 401 `SIGN_IN_REQUIRED`, as expected without an account. |
| `place-assistant?action=status` | HTTP 200; optional photo/location assistance advertised with explicit consent. Status is not proof of a successful live AI completion. |
| `story-audio?action=status` | HTTP 403 `LOCAL_GENERATION_ONLY`; local Whisper transcription is not a production cloud feature. |

Vercel metadata identified production commit `c6ad33e` (10.2.2) as READY at this checkpoint. Preview protection remains enabled. The 10.3 static loader sends same-origin cookies only to normalized `/assets/` and `/demo/` files; API/external URLs retain omitted credentials, redirect rejection and origin checks. Protected previews and anonymous production access require separate validation.

Environment inspection used **decrypt=false** and retained only names, types and target metadata. Production names include Supabase URL/service-role, both provider keys, dedupe/cron/moderation secrets and cloud-generation configuration. `SUPABASE_ANON_KEY` is absent, explaining the separate legacy account API's configured=false. This does not block the service-role-backed anonymous private gift flow. Signup and account demos were not enabled during the audit. No credential values, gift capabilities or signed private-media URLs belong in this document.

Cloud retry requires both the gift capability and signed creator cookie, an approved origin and unexpired access. A fresh attempt requires confirmed terminal failure of the recorded World operation. A stable retry key and transactional locking prevent duplicate reservations/submissions; an ambiguous paid POST is preserved for reconciliation. Input/photo/story/Tripo assets and original expiry remain unchanged. Personal prompts are not copied into retry history. Accounting remains recorded without new artificial creation quotas. Pending upload expires after two hours; finalized private gift access expires after seven days, with separate retention cleanup and a grace period.

The audit found a legacy association oracle in `gp_can_read_memory(mid, uid)`: arbitrary caller-supplied uid could disclose a private ownership/claim association as a boolean. Migration [protect_memory_acl_helpers](../supabase/migrations/20261004230936_protect_memory_acl_helpers.sql) now binds private reads to `auth.uid()` or the effective SQL `service_role`. It keeps public demos, legitimate owner/recipient reads and revocation behavior. Default PUBLIC execution is removed. `gp_new_profile()` execution was revoked from PUBLIC/anon/authenticated, preserving the existing signup trigger.

The migration was applied in production and the [read-only BEGIN/ROLLBACK assertions](../supabase/tests/memory_acl_helpers_production_readonly.sql) passed, without DDL, fixture inserts or Auth writes. Isolated PostgreSQL 18.3/PGlite 0.5.8 executed all seven migrations, [adversarial helper/RLS/trigger tests](../supabase/tests/memory_acl_helpers.sql), the production assertion script and the existing ACL/budget tests. They passed and left zero fixture rows. This local Auth/Storage stand-in is not a managed Supabase signup or multi-connection race test.

Post-migration advisors no longer report the profile trigger exposure. The memory helper still receives generic anon/authenticated SECURITY DEFINER notices because RLS intentionally executes it for demos/self access; its guarded argument behavior is covered by the SQL tests. Eight RLS-without-policy INFO notices describe intentional server-only tables: browser table privileges are denied and service access was verified. Opening those tables or redesigning policies merely to remove an advisor warning would weaken or unnecessarily expand this release. See [Supabase function privileges](https://supabase.com/docs/guides/database/functions) and [trigger privileges](https://www.postgresql.org/docs/current/sql-createtrigger.html).
