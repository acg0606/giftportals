# Anonymous Instant Creator database

`002_cloud_instant.sql` adds an isolated server-only job repository and two private Storage buckets: `gp-instant-private` for inputs and `gp-instant-generated` for generated assets. It does not change the authenticated `001` gift, memory, demo, provider-budget, or storage schema. This is staged preparation; no migration, deployment, credentials lookup, upload, or provider call was performed.

## Trust boundary and activation

The browser has no table privileges, RLS policies, or RPC execution rights for the new tables. Every public request goes through the validated server API, which calls RPCs with its service client. Keep the service-role key, provider keys, capability hashes, and HMAC key on the server. All functions revoke PostgreSQL's default `PUBLIC` execution, and definer functions use `pg_catalog,pg_temp` with qualified application tables. See the [PostgreSQL function security guidance](https://www.postgresql.org/docs/current/sql-createfunction.html).

The lifetime credit caps start at **zero**, so preparing a new job fails closed with `GENERATION_BUDGET`. An administrator must deliberately choose finite caps in `gp_instant_budgets`. Reservations are fixed to the pinned recipe: **100 Tripo credits** for reference plus model and **1,580 World Labs credits** for the world. The full amounts are reserved atomically before the API issues any signed upload URL. Retention can release a reservation only for an expired job that **never left `awaiting_upload` and has no provider stages**. This job was never claimable by a worker, proving no paid submission intent existed. The release uses the same transaction lock as prepare, marks each ledger row `released_at`, and leaves its dedupe tombstone. Repeated cleanup cannot refund twice or reserve that request again. All queued, processing, completed, failed, ambiguous, and deleted submitted jobs retain their conservative lifetime commitments. Actual provider spend is never automatically refunded. Raising a cap is an administrator decision, not a worker retry mechanism. A future provider or recipe change needs reviewed reservation amounts; it cannot silently reuse these limits.

Persistent UTC quotas allow at most 24 new jobs per day globally and two per anonymous browser owner per day. The owner identifier is a hash of a server-issued random browser capability cookie; it is not an IP address. Resetting browser state can change that owner identity, so finite global budgets, storage, and daily quotas remain the backstop. Two worker leases may be live globally. Each job reserves **6 MiB per declared input plus 100 MiB for generated outputs**, against a dedicated 1 GiB cap. This covers the bucket-enforced signed upload maximum even when the client's actual declaration is smaller. Storage reservations are released only after private objects have been removed through the Storage API and the retention tombstone is finalized.

## Capability and dedupe

The client generates one 32-byte base64url request token and persists it while a create is pending. `token_hash` is the lowercase SHA-256 of that exact token, and remains the capability for the resulting job and assets. Hashes are not usable browser capabilities. Read/restore/finalize RPCs require the matching hash and use the same unavailable response for missing jobs and wrong capabilities. Do not rotate the token on a lost response.

The server derives `request_key_hash` with HMAC over the stable request capability hash and the request's dedupe key using a separately configured server key. The separately stored anonymous owner hash supplies browser quotas and is checked on prepare replay. `input_hash` is a SHA-256 commitment to the complete normalized input, including image identities, exact hashes/bytes/MIME, typed text, intent, representation, consent and recipe version. A unique request key either returns the original job for the exact same input and capability or returns `DEDUPE_MISMATCH`; a mismatched owner/capability gets `JOB_UNAVAILABLE`. Dedupe tombstones survive retention, so old requests never silently reserve another paid job. Hash/HMAC values and tokens must be removed from logs and error details.

## RPC contract

All JSON job results contain `id`, `state`, `document`, `stages`, `assets`, `revision`, `lease_id`, `created_at`, `updated_at`, `expires_at`, and `lease_until`. They exclude token, owner, request, and input hashes. The server projects a separate browser DTO and must omit leases, private paths, and unmoderated metadata.

| RPC | Parameters | Result |
| --- | --- | --- |
| `gp_instant_prepare` | `p_id uuid`, `p_token_hash text`, `p_owner_hash text`, `p_request_key_hash text`, `p_input_hash text`, `p_document jsonb`, `p_storage_bytes bigint` | `{job, deduplicated}`; creates `awaiting_upload` and reserves all limits in one transaction |
| `gp_instant_get` | `p_id uuid`, `p_token_hash text` | Job or `JOB_UNAVAILABLE` |
| `gp_instant_lookup` | `p_request_key_hash text`, `p_token_hash text` | Existing job for restoring a pending browser request |
| `gp_instant_finalize_uploads` | `p_id uuid`, `p_token_hash text`, `p_assets jsonb` | Idempotently queues verified uploads; rejects changed asset metadata |
| `gp_instant_claim` | `p_worker_id text`, `p_lease_seconds integer = 60`, `p_id uuid = null` | One job or `null`; `FOR UPDATE SKIP LOCKED`, 30–300 second lease, recommended 240 seconds |
| `gp_instant_begin_submission` | `p_id uuid`, `p_lease_id uuid`, `p_revision bigint`, `p_stage text` | Persists the stage's `submitting` intent and returns the new revision before any paid POST |
| `gp_instant_update` | `p_id uuid`, `p_lease_id uuid`, `p_revision bigint`, `p_state text`, `p_document jsonb`, `p_stages jsonb`, `p_assets jsonb`, `p_release_lease boolean = true` | Compare-and-swap update; stale leases/revisions fail; final worker call releases its lease |
| `gp_instant_retention` | `p_limit integer = 100` | Up to 100 expired dedicated job prefixes and asset manifests to remove through Storage |
| `gp_instant_purge` | `p_id uuid` | Idempotently clears private documents/assets and releases storage after deletion; keeps tombstones and budgets |

`gp_instant_job_json`, `gp_instant_validate_assets`, and `gp_instant_expire_leases` are internal helpers without service RPC execution grants.

A capability-authorized browser **POST advance** first validates the requested job with `gp_instant_get(id, token_hash)`, then claims with that same non-null `p_id`. The SQL ID predicate applies outside every eligible state branch, so this operation can lease only the requested gift. Its expired-lease handling also receives the same ID and cannot change another job. A missing, busy, terminal or not-yet-due target returns no claimed job; it must not fall back to claiming from the global queue. Secret-authorized background workers may omit `p_id` to claim and expire leases globally. The public job GET only reads/projects results and signs approved assets; it never claims, polls providers, begins submissions, or changes job state.

## Inputs, moderation and immutable storage

`document.images` is a normalized array of one to three declarations: `{id: 'original'|'object'|'world', sha256, mime, bytes}`. `original` is required; IDs are unique; inputs are JPEG, PNG or WebP, each at most 6 MiB. `p_storage_bytes` must equal their summed lengths. Other initial fields contain validated text, intent, representation, `needsReference`, curiosity/example selection and the pinned generation settings. Every initial document key/value remains immutable. The worker appends metadata such as `photoSafety`, `objectSafety`, `derivedReference`, `worldSemantics`, `splatQuality`, and `colliderStatus`; the read-only DTO projection merges appropriate metadata into generation settings.

The prepare response signs only declared input paths in `gp-instant-private` with Storage upsert disabled. This input bucket enforces a 6 MiB file maximum; generated assets use the separate `gp-instant-generated` bucket with a 100 MiB file maximum. A signed upload cannot bind the client's claimed content length, so the reservation covers the maximum for every issued input path. Input paths are exactly `<job UUID>/input/<image ID>-<SHA-256>.<jpg|png|webp>`. The finalize server must download each private original, check its length, magic bytes, MIME, and SHA-256, then pass an object keyed by the image IDs to the RPC. SQL compares every declaration and validates the exact path. The upload token alone does not authorize job reads or paid generation. Supabase's [signed upload URLs](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl) work without an authenticated session; both dedicated buckets remain [private](https://supabase.com/docs/guides/storage/buckets/fundamentals) and a restrictive policy blocks direct anonymous/authenticated bucket access even if unrelated permissive policies exist.

Finalization only queues work. Uploaded originals remain private and quarantined. Before a paid submission, the worker must store a trusted `photoSafety` report with protocol `giftportals-cloud-vision-v1`, a model version, overall `allow`, and an allowed ordinary result matching every declared image ID and hash. SQL rechecks those commitments before beginning each submission. A generated reference also requires an allowed `objectSafety` result matching its exact hash before model submission. The service must validate the complete classifier response and must not accept a browser-supplied report. The repository does not substitute for that classifier.

Generated paths are exactly `<job UUID>/generated/<SHA-256>.<png|jpg|webp|glb|spz>`, and writes use upsert disabled. References are PNG/JPEG; panoramas may also be WebP. On an existing object, compare the stored bytes/hash rather than overwriting it. Asset keys and metadata are append-only: generated keys are `reference`, `model`, `panorama`, `collider`, and **`generated-world`**. If there is an input place photo at `assets.world`, it remains there unchanged; the generated SPZ uses `generated-world`. A legacy `world` SPZ is permitted only when there is no uploaded `world` entry. Outputs may total at most the reserved bytes, and each object is bounded by 100 MiB. A stage cannot complete before its required generated asset is present. The worker must validate GLB/SPZ/image content and provider/CDN allowlists before uploading. Serve outputs through capability-authorized endpoints; never sign or expose original/reference imagery before its matching moderation approval.

## State machine and recovery

Jobs move from `awaiting_upload` to `queued`, then leased `processing`. Jobs finish as `completed`, `partial`, or `failed`; `submission_uncertain` means a paid task might exist but no trustworthy task ID was saved. Queued admission may be repeated for transient credit availability only while no stage submission has begun. The provider stage keys are `tripo-reference`, `tripo`, and `worldlabs`. An absent stage is pending. A stage first enters `submitting` only through `gp_instant_begin_submission`, then enters `processing` with its recorded `taskId`, and finally `completed` or `failed`. `submittedAt`, a recorded task ID, and a recorded result ID cannot change. Terminal stages never reset. A failure before any paid call is an immutable `document.stageFailures[stage]` error marker, not a fabricated submitted stage; it also blocks that stage from subsequently starting.

Persist `submitting` **before** calling the provider. Await the begin RPC successfully, use its returned revision, issue exactly one POST, and save the task ID with a CAS update. A timeout, dropped response, or crash after that POST never causes another POST. An expired lease containing `submitting` becomes `submission_uncertain` and loses its lease. A later worker may only poll already recorded processing task IDs; it cannot begin an uncertain stage again. Other recorded stages may finish, leaving a partial result. Operator reconciliation must be deliberate and cannot erase the original submission intent. No browser polling handler may initiate generation or fall through to the older authenticated cloud pipeline.

Known task polling and idempotent output downloads are safe to repeat. Keep the same task ID, progress monotonically increases, and existing assets cannot change. Temporary poll/download errors may leave the stage `processing`; release the lease and poll the existing task on a later tick. A stale worker cannot update a reclaimed job because every mutation checks both lease UUID and revision. There is no transaction spanning a provider HTTP call; the durable intent and conservative uncertainty state cover that boundary.

## Retention and validation

Prepared uploads expire after two hours; finalized jobs after seven days. Read/restore/finalize refuse expired jobs. Retention waits a further two hours before deleting a prefix, covering a last two-hour signed upload token issued before expiration. The server must refuse to issue upload URLs after the prepare expiration. Its transaction releases paid reservations only for provably unsubmitted `awaiting_upload` jobs, while **storage remains reserved until deletion**. Cleanup must list and remove **all** objects within the exact dedicated `<UUID>/` prefix in **both** new buckets, including inputs uploaded before finalization; the manifest alone cannot enumerate unfinalized objects. Remove objects through Supabase Storage, not direct SQL against its metadata. Only after confirmed deletion call `gp_instant_purge`. Keep capability/dedupe hashes, submission history, quotas and all reservation audit rows so retention cannot enable duplicate submissions. A server scheduler must actually run retention and cleanup; expiry alone does not remove files or release storage. Existing unrelated buckets and authenticated gift/demo rows are out of scope.

The dedicated worker endpoint supports **GET or POST with the exact `Authorization: Bearer <CRON_SECRET>`**. An authenticated Vercel cron GET may advance the global queue; manual or external schedulers may use the same secret-authorized POST. An optional daily Vercel cron provides a background sweep, while capability-authorized browser POST advance calls can keep the active gift progressing promptly. A daily sweep alone is not an interactive generation cadence. Include actual retention plus both-bucket cleanup in the scheduled server work; scheduler authentication is distinct from a browser job capability. Public job GET polling remains read-only. Confirm the supported cron cadence for the deployment plan before choosing the final schedule.

Run the offline checks with `node --test api/tests/cloud-instant-sql.test.mjs`. They verify the staged SQL contract and security guardrails without network access. **SQL execution and concurrency were not verified here: no local PostgreSQL executable was available.** Before deployment, apply both migrations to a disposable Supabase project and exercise: wrong capabilities; same-request exact replay; altered input replay; concurrent owner/global quota admission; zero/insufficient budgets; two simultaneous workers; stale revision/lease rejection; expired `submitting` with no second POST; recorded-task-only polling; immutable asset conflict; moderation hash mismatch; expired capability reads; and retention prefix deletion. Confirm anonymous and authenticated roles cannot select new tables, invoke new RPCs, or access the private bucket. Do not use the existing confirmed submission database as that test fixture.
